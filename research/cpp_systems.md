# C++ / low-latency / systems knowledge in quant-dev and HFT SWE interviews: what is asked, how deep, and how to prepare efficiently

Research date: 2026-09-01.

## 0. Method and evidence quality (read this first)

**How this was gathered.** ~8 web searches (the session's search budget was exhausted early) plus ~90 page fetches. Almost every non-GitHub domain (Reddit, Blind, Glassdoor, 1point3acres, QuantNet, Medium, HN, eFinancialCareers, Substack, YouTube, company career pages, quantt/techinterview/dataford aggregators, cppreference) was blocked by the network egress proxy. So the evidence base is:

1. **First-person interview write-ups hosted on GitHub** (IIT Delhi intern-season write-ups, personal blogs mirrored on GitHub, `Shivam5022/Interview-Experiences`, `Leader-board/OA-and-Interviews`, `Lazar-Ilic`). These are the strongest evidence here: specific people, specific rounds, specific questions.
2. **Curated "mined" question banks on GitHub** that label each item as REAL (candidate-reported) vs PRACTICE (prep-site listicle), notably `pushpa-kumar/placement-prep` (which itself mined Blind, LeetCode Discuss, Glassdoor, 1point3acres, AmbitionBox, GeeksforGeeks, Wall Street Oasis) and `ankitkushawaha1000/HFT` (labels `official / inferred / anecdotal / general-prep`; the author of the placement-prep repo warns it is possibly AI-assisted and that *every* item is anecdotal or inferred). Medium-strength evidence: second-hand, but with provenance labels.
3. **Primary technical sources** actually read: Carl Cook's CppCon 2017 slide deck (full text extracted), practitioner notes on David Gross's Meeting C++ 2022 talk, `rigtorp/SPSCQueue` README, `dendibakh/perf-ninja` README.
4. **Search-engine snippets** of blocked pages (HRT's official interview blog, Citadel Securities' engineering-interview page, Blind/Glassdoor threads, quantt/techinterview/hackerprep guides). Weak-to-medium: I could not read the pages, only the snippet the search engine returned.
5. **Practitioner opinions on prep resources** from GitHub-hosted blogs (Sandor Dargo, XhovaniM8's getcracked.io review, `Unays7/HFT-Interview-Prep` commentary, `quasar-chunawala/quantdev`).

Confidence tags used below: **[S]** strong (first-person or primary source read in full), **[M]** medium (labelled second-hand compilation or official-page snippet), **[W]** weak (unlabelled aggregator / prep-site / possibly AI-generated).

## 2. The questions, categorised

Frequency judgement = how often the item appears in REAL/first-person reports above (not in prep-site lists).

### (a) Language semantics
Very common: virtual functions / vtable layout (incl. multiple inheritance, diamond) [HRT, IMC, Optiver, Citadel, QuantBox, JPMC]; smart pointers - implement `shared_ptr`/`unique_ptr`, refcount atomics, `weak_ptr` cycles, hot-path cost [Graviton, QuantBox, AlphaGrep, IMC, Citadel, DE Shaw, Point72]; RAII (scope guards, lock guards, file handles) [Jump, Squarepoint]; move semantics, `std::move` vs `std::forward`, RVO/copy elision, "when does `std::move` not help / hurt" [DRW, Squarepoint, Citadel, Optiver]; rule of 0/3/5 [Citadel, NVIDIA]; `inline` "mainly means multiple definitions permitted" vs inlining [HRT x3, Carl Cook's slides]; implement `std::vector` / `push_back` / a `String` class [HRT, SIG, AlphaGrep, QuantBox, Squarepoint]; STL internals - `map` vs `unordered_map` (red-black tree vs hash), `vector` vs `list` vs `deque` [HRT, Citadel, IMC, DE Shaw]; `new` vs `malloc` vs placement new [Citadel, Quadeye, Optiver]; SSO / `std::string` internals [HRT].
Common: templates - CRTP vs virtual, specialisation vs overloading, SFINAE/concepts, `constexpr` at compile time, implement `std::variant` [IMC, HRT, "an HFT firm"]; `volatile` vs `std::atomic` [Citadel, Intel]; exceptions on the hot path (zero-cost-until-thrown; Carl Cook measured >=1.5 us when thrown) [Citadel `inferred`, Jump `inferred`]; UB spotting (dangling pointer/reference, signed overflow, strict aliasing, iterator invalidation) [Optiver anecdotal, SAP, NVIDIA]; `std::function` vs function pointer / `inplace_function` [Citadel per quantt; Carl Cook slide 46-47]; static local init overhead, lambdas [Carl Cook].
Rare in reports: `consteval`, modules, coroutines, ranges.

### (b) Memory / cache / hardware
Very common: cache hierarchy and latencies, cache line = 64 B, false sharing (diagnose + `alignas(64)`) [HRT, Citadel, IMC, Jump, Optiver, Graviton]; struct layout / padding / packing / "which struct is bigger" / reorder fields for cache [Optiver OA, XTX, Jump, HRT]; branch prediction, branchless code (branchless binary search) [Graviton, Tower, IMC]; virtual memory, paging, TLB, huge pages, page faults, `sbrk`/`mmap`, demand paging [HRT, Tower, Squarepoint, DE Shaw]; `malloc` internals, pools/arenas, why no allocation on the hot path [HRT, QuantBox, Citadel, Jump, IMC, Optiver].
Common: MESI / cache coherence [IMC, Citadel `inferred`, QuantBox "cache coherence types"]; pipelining, RISC vs CISC, pipeline stalls [Tower, Graviton]; NUMA, prefetching, SoA vs AoS [mostly `inferred`/PRACTICE; David Gross and Carl Cook talks cover them].
"Order these by latency" style: IMC ("sort fastest to slowest: cache, RAM, heap allocation, addition, disk").

### (c) Concurrency
Very common: implement a lock-free SPSC ring buffer with atomics and correct acquire/release [Headlands REAL, Citadel + HRT REAL, Optiver anecdotal, IMC anecdotal, Jump inferred, Citadel phone screen "ring buffer"]; memory orderings relaxed/acquire/release/seq_cst and what they cost on x86 vs ARM [DRW, Citadel, HRT, IMC]; mutex vs spinlock vs condition variable [DRW, QuantBox, Squarepoint]; "two threads increment a counter, result < 2N, why" / atomics vs mutex [HRT]; thread-safe / bounded queue optimisation [Squarepoint, Citadel, Microsoft]; "is multithreading always faster" [IMC]; SPMC ring buffer [Citadel REAL]; producer-consumer with locks (bank transfers) [Graviton]; sum/prefix-sum with p threads [Tower intern].
Common: ABA, hazard pointers, RCU [QuantBox REAL; Citadel/Optiver `inferred`]; seqlocks (David Gross talk); thread affinity / CPU pinning and "why pinning alone is incomplete" [Citadel REAL, HRT `inferred`].
Note: HRT-style "false sharing wrecks a lock-free counter" is reported as a hard filter.

### (d) OS / Linux / networking
Very common: TCP vs UDP and why multicast for market data [HRT, Optiver, Squarepoint, DRW, Flow Traders]; process vs thread, user vs kernel threads, IPC, named pipes, shared memory [HRT, Point72]; virtual memory / page tables / segfaults [HRT, Squarepoint]; system calls at assembly level, what `cout` does [Tower]; `epoll` vs `select`/`poll` [DRW]; TCP state machine [Squarepoint]; DNS, `ping`, port-open checks, inode/RAID/links [HRT, Tower, Flow Traders].
Common: kernel bypass (DPDK / Solarflare OpenOnload / ef_vi), busy polling, hardware timestamping, RDMA [Jump, IMC, HRT - mostly `inferred`; Carl Cook's measurement slides]; "walk a packet from NIC to strategy" [Optiver/IMC per techinterview]; CPU isolation, `isolcpus`, interrupt affinity, C-states/P-states (David Gross).
Rare: io_uring, eBPF (listed in prep repos, never in a reported question).

### (e) Design
Very common: **limit order book** - add/cancel/modify/match, O(1) cancel via hash map of order id -> intrusive list node, price levels as sorted structure or array/bitmap, "why not just `std::map`" (heap allocation per node, pointer chasing, cache misses at 10k levels; cancels dominate) [IMC signature question, Citadel, Jump take-home, Tower, Two Sigma, Optiver, SIG, DRW thread-safe variant, Citadel multi-exchange BBO/NBBO]; **matching engine** with price-time priority and partial fills [IMC, Two Sigma, Jump]; **market-data feed handler** (UDP multicast, sequence gaps, recovery, normalisation, fan-out) [Citadel, XTX, Optiver, Jump, HRT, Flow Traders risk server]; pre-trade risk / kill switch with a latency budget [HRT 1 ms risk system REAL; others `inferred`]; order gateway / OMS with reconnect and throttling [Jump `inferred`, Optiver order-entry tool]; "design a trading system Amsterdam -> Frankfurt" (co-location, automation) [Optiver intern]; real-time price grid UI [Optiver].
Common: rate limiter / order throttler [HRT, Blind mention]; LRU cache [Citadel, HRT, Jump]; message-bus / SPMC event distribution; logging without latency (David Gross "flight recorder", non-temporal stores in PRACTICE lists).
FIX/ITCH parsing: zero-copy ITCH decode with `#pragma pack`, `bswap`, strict-aliasing caveats appears in mock-interview material [W] and in "feed message parser + sequence-gap handling" prep lists; DRW's binary struct serialisation/endianness question is the closest REAL item.

### (f) Debugging / reading code / spotting bugs
Citadel's 2-hour "obfuscated C++ debugging/optimisation" onsite round [M, multiple Blind reports]; Squarepoint "debug a dummy `vector`" and "count ctor/move/assignment calls in this snippet" [S]; Akuna OA "refactor a buggy object pool (races, double-free, ABA, leaks)" [M]; DRW OA "bug-finding" questions [S]; Optiver "debug this code: what UB exists" [anecdotal]; Tower "analyse this inefficient C++ for branch prediction" [S]; Graviton "remove branching from this snippet" [S]; Stripe-style bug-squash round [S]; NVIDIA "code with intentional memory bugs" [M]; "here is a lock-free queue with a subtle bug - find it" [W, hieptran playbook].

### (g) Performance estimation
"Sort these operations by latency" [IMC REAL]; "how long does the tick-to-trade path take and where does the time go" [W, techinterview/hieptran]; latency-number tables are ubiquitous in prep material: L1 ~1 ns, L2 ~3-4 ns, L3 ~12-15 ns, cross-core cache-line transfer ~40-80 ns, DRAM ~60-100 ns, branch mispredict ~15-20 cycles, heap alloc ~80-200 ns, wire-to-wire software floor ~2.5 us (Carl Cook, 2017), `std::pow` 53 ns vs 478 us pathological (Carl Cook), `unordered_map` find 14-24 ns vs hybrid array_map 7-9 ns (Carl Cook). Only IMC's ordering question is confirmed REAL; the rest is what candidates are told to memorise.

### (h) Build / tooling
Reported: `perf`/`perf c2c`/flamegraphs for false sharing and tail latency [HRT-style, `inferred`]; sanitizers/valgrind [Spotify, Shivam prep]; compiler flags (`-O2` vs `-O3`, LTO, PGO), reading assembly / Compiler Explorer (Carl Cook's talk uses it; Tower expects "assembly-level insights"; Graviton expects branchless codegen); shared vs static libraries, ODR/inline in headers [Tower, ARM]. Almost no firm asks about build systems.

## 3. Depth expected, and which firms go deepest

**Firms that grill hardest on C++ internals + hardware (multiple independent REAL reports):** HRT (phone screen is pure C++/OS depth with no algorithms), Citadel Securities (std-lib internals on the phone, obfuscated-code debugging onsite, senior interviewers pivot to multithreading/systems), Jump (kernel/concurrency/CPU architecture alongside DSA; hardware co-design), IMC (matching engine + vtable + smart-pointer internals + false sharing), Optiver (explicit C++ syntax/memory test and hardware/concurrency test in the pipeline). Indian HFTs (Graviton, QuantBox, Quadeye systems track) are at least as deep - branchless codegen, RCU, memory reordering - even for interns. [S/M]

**Trivia vs design:** HRT, Squarepoint, Tower and QuantBox lean toward "explain the machine" trivia (inline, malloc, TLB, RISC pipelines). Citadel, IMC, Jump, Optiver lean toward implement-it (ring buffer, pool, order book) plus design rounds (feed handler, risk, OMS). Jane Street (any language) and Two Sigma are coding/design heavy and do not probe C++ internals; Virtu and SIG lean toward brainteasers and "real-life" OOP problems with light C++ [M].

**Multi-strat / pod shops (Squarepoint, Millennium, Point72/Cubist, DRW's non-HFT desks):** the same vocabulary but shallower - CS trivia lists, `shared_ptr`/`weak_ptr`/`unordered_map` questions, TCP socket reading, shared-memory IPC [S/M]. Squarepoint's three technical rounds are a good "floor" model for a C++ quant-dev loop.

**Typical loop shape (converges across sources):** OA (HackerRank/Codility/CodeSignal, 2-4 DSA problems, roughly CF 1600-1800 / LC medium-hard; some OAs add C++/OS MCQs) -> 1-2 phone screens (DSA + C++ concepts, sometimes pure C++/OS) -> onsite/superday of 4-6 rounds: algorithms, C++/systems depth, low-latency design, probability/brainteasers (firm-dependent), behavioural. Citadel reportedly cancels the rest of the loop after one weak round.

**Contradictions worth noting.**
- Difficulty of algorithms: techinterview claims "2400+ Codeforces" for Jump; every first-person OA report says CF 1600-1800 / LC medium, and HRT's phone screens are reported as "no algorithms". The prep-site claim looks inflated.
- Blind threads say "HFTs don't typically ask LeetCode... they ask you to write vector/deque/smart pointers, order throttler, order book" while other Blind threads say "early rounds are mainly LeetCode + brain teasers". Both are consistent with the REAL data: OAs and junior interviewers use LeetCode; senior interviewers and later rounds use implement-a-container / systems.
- Jane Street: prep sites list it among "low-latency C++" firms; the only real data shows language-agnostic coding/design rounds with no C++ internals.
- ankitkushawaha1000/HFT presents polished per-firm round lists, but its own `data/cpp-questions.json` carries zero `official` or `anecdotal` labels (18 general-prep, 9 inferred-from-JD, 3 general), and placement-prep flags it as possibly AI-assisted. Its "SPSC / MESI / NUMA / kernel bypass" items are plausible but are inferences from job descriptions, not reports.

## 5. Prep resources and what practitioners say about them

**Books**
- *Effective Modern C++* (Meyers): recommended by every curated list (Unays7, cybergeekgyan, ankitkushawaha sources, quantt snippet). Nobody reports it as sufficient; it covers move semantics/smart pointers/`constexpr`/lambdas well, nothing on hardware. [M]
- *C++ Concurrency in Action* (Williams): universally listed as *the* memory-model/atomics reference (Unays7, cybergeekgyan, ankitkushawaha, shreejitverma canon, quasar-chunawala). Chapters 5 (memory model) and 7 (lock-free) are the interview-relevant core. [M]
- *What Every Programmer Should Know About Memory* (Drepper): listed by Unays7, shreejitverma canon, hieptran; long and dated (2007) - practitioners cite it for cache/NUMA/prefetch fundamentals, not as a read-cover-to-cover item. [M]
- *Operating Systems: Three Easy Pieces* (free): Unays7's top OS pick; matches the HRT/Squarepoint/Tower OS trivia (paging, TLB, threads, IPC). [M]
- Algorithmica *HPC* (free, https://en.algorithmica.org/hpc/): Unays7 calls it "AMAZING"; covers branchless code, cache, SIMD - the Graviton/Tower style questions. [M]
- *Performance Analysis and Tuning on Modern CPUs* (Bakhvalov, free) + perf-ninja labs: Unays7 "do the labs and watch vids after reading book"; labs take 30 min-4 h each, cover false sharing, huge pages, alignment, virtual-call mispredicts, LTO/PGO. https://github.com/dendibakh/perf-ninja [S]
- *Optimizing software in C++* (Agner Fog, free), *C++ High Performance* (Andrist/Sehr), *Inside the Machine* (Stokes), *Systems Performance* (Gregg), *TCP/IP Illustrated*, *The Linux Programming Interface*: listed by Unays7 / cybergeekgyan / shreejitverma; no first-person "this got me through" statements. [W/M]
- *Developing High-Frequency Trading Systems* (Donadio et al.) and *Building Low Latency Applications with C++* (Ghosh): listed as domain context; a Substack review of the Ghosh book exists (https://lucisqr.substack.com/p/review-of-building-low-latency-applications) but was blocked. [W]
- *Ace the Trading Systems Developer Interview (C++ Edition)* (Dennis Thompson): Unays7's verdict - "good for quick interview prep to brush up on C++ trivia etc, not a resource to rely on but will help if you forget some language-specific stuff + OS/Networking qs". [S-ish, one practitioner]
- *Trading and Exchanges* (Harris) for order-book/market-structure vocabulary [M].

**Talks**
- Carl Cook, CppCon 2017, *When a Microsecond Is an Eternity* (Optiver) - "Goated" (Unays7); read in full here. Contents map almost 1:1 onto interview topics: slow-path removal via error flags with `noinline` error handlers; template-based configuration instead of virtual/branches; lambdas inline; preallocated pools, reuse instead of `delete` (glibc `free` has 400 lines of bookkeeping), delete large objects on another thread; exceptions zero-cost unless thrown (>=1.5 us when thrown); avoid multithreading on the hot path, if needed use SPSC queues and copies; denormalise data into one cache line; `unordered_map` chaining vs open addressing vs hybrid (14-24 ns vs 7-9 ns find); `inline` means "multiple definitions permitted", use `always_inline`/`noinline` and measure; keep I-cache/D-cache and branch predictor warm with a dummy path; disable hyper-threading, choose L3 neighbours; placement-new null check (pre-gcc-7.1), SSO/COW `std::string` ABI, static-local guard (5-10%), `std::function` allocates -> `inplace_function`, `std::pow` slow path; measurement: sampling/instrumentation profilers and microbenchmarks all miss the point - measure wire-to-wire with hardware-timestamping switches; floor ~2.5 us wire-to-wire in 2017. Slides: https://github.com/CppCon/CppCon2017/blob/master/Presentations/When%20a%20Microsecond%20Is%20an%20Eternity/When%20a%20Microsecond%20Is%20an%20Eternity%20-%20Carl%20Cook%20-%20CppCon%202017.pdf ; video https://www.youtube.com/watch?v=NH1Tta7purM
- David Gross, Meeting C++ 2022, *Trading at light speed* (Optiver) - "Good watch" (Unays7). Practitioner notes: "performance is a design decision, not a fix"; replace node-based containers with a chunked `stable_vector`; seqlocks for 1-producer/many-consumer (~100 readers); per-slot seqlock SPMC ring with <100 ns jitter; P-states (idle CPUs at 400 MHz) and C-states evict caches; "if you don't measure it in production it doesn't exist" - RDTSC + lock-free metrics. https://github.com/romz-pl/posts-linkedin/blob/main/doc/099-meetingcpp-low-latency/README.md ; video https://www.youtube.com/watch?v=8uAW5FQtcvE
- Also listed in prep repos: Timur Doumler and Fedor Pikus CppCon talks (concurrency/perf), Martin Thompson "Mechanical Sympathy", Jane Street "How to Build an Exchange". [M]

**Blogs / code**
- rigtorp.se (Erik Rigtorp) and `rigtorp/SPSCQueue`: cited by Unays7 and quasar-chunawala; the README documents the exact SPSC design interviewers expect (padded head/tail on separate cache lines, cached indices to cut coherence traffic, 133 ns RTT). https://github.com/rigtorp/SPSCQueue [S]
- learncpp.com: recommended for OOP fundamentals by IIT Delhi students (Optiver/Jane Street clean-code rounds) and DE Shaw intern. [S]
- Compiler Explorer: implicitly required - Carl Cook's talk, Tower's "assembly-level insights", Graviton's "branchless compiled code". [M]
- highload.fun for optimisation practice (Unays7). [M]

**Courses / paid**
- getcracked.io (Coding Jesus): one reviewer (XhovaniM8) - covers OS, architecture, concurrency, networking, C++ systems; coding problems force real implementations ("lock-free queues, order books, mutex primitives", single-digit success rates); $20/mo, $179/yr, $299 lifetime; "helped me land interviews at multiple quant trading firms, HFT shops" but "not a substitute for general algo breadth" and he still failed on implementation speed; 4/5. Sandor Dargo (C++ author) praises the quiz format ("every option maps to a real misconception") for an intermediate-C++ roadmap, no HFT-specific claim. quasar-chunawala lists it for "puzzles testing C++, OS and computer architecture". No Coding Jesus YouTube content could be fetched. https://github.com/XhovaniM8/xhovanim8.github.io/blob/main/_posts/2025-09-07-getcracked-io.md ; https://github.com/sandordargo/sandordargo.github.io/blob/master/_posts/2026-8-28-getcracked-intermediate-cpp-roadmap.md [M]
- "Quantitative Developer" style courses (QuantInsti EPAT, quantlabsnet, hackerprep): only marketing pages surfaced; no practitioner endorsement found. [W]
- Grokking / Alex Xu system design: Unays7 lists them but notes they are long; HFT design rounds are "not web-scale design" (hieptran) - the relevant material is order book / feed handler / risk, which these books do not cover. [M]

**Explicit "wasted time" signals** (thin, but consistent): memorising CppCon trivia or latency tables without having built and measured something ("show, don't tell" - hieptran; "measure measure measure" - Cook); generic web-scale system-design courses; reading Drepper cover to cover; the ankitkushawaha-style 280-question banks (its author's own labels show none are confirmed real); prep-site "2400 Codeforces" panic.

## 6. Minimal viable syllabus and time investment

**Reported time budgets.**
- IIT Delhi placement (new grad, HFT dev/quant/SDE): ~4 months (Aug-Nov), mostly LC-hard under 30-min windows plus targeted C++ YouTube for stack/heap, move vs copy, smart pointers, virtual destructors/vtable, `constexpr`, templates, padding/packing, casting, threads. https://github.com/anirudhakulkarni/Placements-2024 [S]
- ankitkushawaha (3-yr C++ at Deutsche Bank, targeting senior HFT roles): 30-day plan at 2-3 h/day + one long weekend session; week 2 = C++ (value categories, lifetime, templates/concepts, SPSC + acquire/release, `pmr`/arenas, STL perf), week 3 = cache/TLB models, feed-handler architecture, sequencing/gap recovery, affinity/backpressure, two full design deliveries; week 4 = mock loops. 60-day variant exists. https://github.com/ankitkushawaha1000/HFT/blob/main/content/study-plans/30-day-plan.md [M, self-designed]
- hieptran playbook (composite, not first-person): 6 months - 2 months memory model/UB/move/abstraction costs, 1 month hand-building SPSC ring buffer + arena allocator + lock-free stack, 1 month cache/false sharing/branch prediction/kernel bypass, algorithms + probability throughout, ship a measured GitHub project. [W]
- IIT Delhi tips: "at least 3 weeks" for firm-specific prep, don't cram the last week. [S]
- perf-ninja labs: 30 min-4 h each. [S]

**Minimal viable syllabus (what the REAL data says you must be able to do live), ordered by evidence weight**

1. Implement from scratch, in 20-30 min, bug-free: `unique_ptr`, `shared_ptr` (atomic refcount, control block, `weak_ptr`), a `vector` with `push_back`/`reserve`/rule-of-5, an LRU cache, a fixed-size object pool, and an SPSC ring buffer with `alignas(64)` head/tail and acquire/release. (HRT, Citadel, IMC, Optiver, Headlands, Graviton, QuantBox, AlphaGrep, SIG, Akuna.)
2. Explain the machine: vtable layout (incl. MI), object layout/padding, stack vs heap, `malloc` internals, `sbrk`/`mmap`, demand paging, page faults, TLB and huge pages, cache hierarchy with rough numbers, false sharing and MESI, branch prediction and how to write branchless code, `inline` vs inlining, SSO/COW strings, exceptions cost. (HRT, Tower, Squarepoint, Citadel, IMC, Graviton, QuantBox.)
3. Memory model: relaxed/acquire/release/seq_cst, what each costs on x86 vs ARM, `volatile` vs atomic, mutex vs spinlock vs condvar, ABA, why the counter came out short. (Citadel, HRT, DRW, IMC, QuantBox.)
4. Linux/networking basics: process vs thread, IPC/shared memory, `epoll`, TCP vs UDP and why multicast, TCP state machine, what a syscall is at the assembly level; conceptual kernel bypass and CPU isolation. (HRT, DRW, Squarepoint, Tower, Optiver/IMC.)
5. Design: an order book (why not `std::map`; O(1) cancel; price-level arrays/intrusive lists), a matching engine with price-time priority and partial fills, a multicast feed handler with gap detection/recovery, a pre-trade risk check with a latency budget. (IMC, Citadel, Jump, Optiver, Tower, XTX, HRT, SIG.)
6. Debug/read code: spot dangling pointers, UB, iterator invalidation, missing destructors, data races, double-free in a given snippet; count ctor/move calls; explain what a compiler will do. (Citadel, Squarepoint, Akuna, DRW, Optiver.)
7. Keep DSA at LC-medium/hard, CF ~1600-1800 speed - it gates every OA and most phone screens.

**A time-efficient plan (synthesis of the above, ~6-8 weeks at 10-15 h/week for someone who already writes C++ daily; roughly double for a new grad who also needs DSA volume).**
- Weeks 1-2: OSTEP virtual-memory + concurrency chapters; Effective Modern C++ items on move/smart pointers/`constexpr`; Concurrency in Action ch. 5 and 7; watch Carl Cook and David Gross once each and write down every technique.
- Weeks 3-4: build the six data structures in item 1 with tests; benchmark them with `perf stat`/Google Benchmark and inspect codegen in Compiler Explorer; do 4-6 perf-ninja labs (false sharing, alignment, branch, virtual calls).
- Weeks 5-6: build an order book + matching engine + ITCH-style parser project with measured p50/p99 numbers; rehearse the feed-handler and risk-system design talk-tracks (30 and 60 min versions).
- Throughout: 3-5 LC medium/hard per week; one mock "explain the machine" oral exam per week using the HRT/Tower/Squarepoint question lists above; if you want a structured question bank, getcracked.io is the only paid product with a positive practitioner review here.
